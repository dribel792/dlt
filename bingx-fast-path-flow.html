BingX × DLT × Anduin — Integration Proposal

Fast-Path Execution: Latency-Optimized Flow for Securitized Perps on BingX

October 2026 · Working draft v0.2 — supplements the Technical Integration & Flow of Funds doc (v0.3); addresses the BingX MM latency concern

The BingX MM's concern with the baseline chain (User → BingX → DLT → Anduin → MM, and the same hops back for quotes) is that round-trip latency in both directions forces either wider spreads, larger slippage buffers, or worse MM PnL. This document restructures the flow so that no latency-critical hop runs through DLT, while the regulatory order chain remains exactly the baseline chain. Two changes: (1) the quote stream goes MM → Anduin → BingX directly, with Anduin as a thin validating proxy; (2) on order entry, BingX fires a parallel hedge trigger straight to Anduin so the MM has already executed by the time the client order arrives through the regulatory chain — the chain then plays back execution details instead of waiting for a fresh price. The model is not RFQ — there is no per-order quote request and response. Anduin STPs / proxies everything straight into the MM; the MM's only job is to make sure the order executes, and all execution information is passed on to DLT.

1 · The principle — two tracks per order

TrackWhat runs on itLatency requirement
Fast path operational Quote streaming (MM → Anduin → BingX) and the hedge trigger on order entry (BingX → Anduin → MM). Carries no client order and no securities trade — it is the issuer's own hedging machinery, fed by an early signal from the distribution frontend. Milliseconds — co-located, WS/FIX, no intermediate consumer.
Regulatory path legal The client order and the securities trade: BingX (tied agent) RTO → DLT (executing broker) STP/back-to-back → Anduin (issuer, counterparty of the cert trade). Booking, fee collection, T+0 reporting — unchanged from the baseline doc. Not latency-critical anymore — the price is already locked by the fast path when the order arrives; this track confirms and books.

Why this kills the latency problem

In the baseline, the MM quotes a price at T0 and fills the hedge at T0 + (4 order hops) — the gap is MM risk, priced into the spread. In the fast path, the time between the user clicking and the MM filling is two co-located hops (BingX → Anduin → MM, with Anduin proxying the MM's own execution API). The MM prices against a gap of milliseconds, not of a full multi-party round trip — so it can quote tighter spreads with less slippage reserve. The regulatory chain stops being a pricing constraint entirely.

2 · Quoting flow — DLT out of the streaming path

The MM streams the cert books (or perp books, per Flow 1/Flow 2 of the baseline doc) to Anduin, which proxies the stream directly to BingX — rendered to the user as the reference price. Inline validation of the stream against Anduin's published levels is optional — Anduin is willing to skip it and run the checks asynchronously on the archived stream instead, keeping the proxy a pure pass-through; every tick lands in the insert-only quote archive either way. DLT receives a non-latency-critical mirror of the same stream for surveillance and reconciliation; it is no longer a hop in the display chain.

3 · Execution flow — hedge trigger first, order chain plays back

On order entry BingX does two things simultaneously: it fires the hedge trigger to Anduin (fast path) and transmits the client order to DLT (regulatory path). Both carry the same client_order_ref. There is no RFQ step — Anduin STPs / proxies the order straight into the MM, whose only job is to execute. By the time the RTO'd client order arrives via DLT, the MM fill already exists, and Anduin matches it by reference to fix the cert execution price. All execution information is then passed on to DLT: Anduin → DLT (books T+0, collects fee) → BingX → user.

Timing summary

  1. t=0 — user clicks. BingX stamps client_order_ref.
  2. t+ms — hedge trigger reaches the MM via Anduin's proxy; MM executes against the price it is itself streaming. Slippage window ≈ co-located round trip.
  3. t+X — client order arrives at Anduin via DLT. X is irrelevant to pricing: the fill is locked, X only delays the booking confirmation.
  4. t+X+ε — trade booked T+0 at DLT, execution details back to the user. The user-visible confirmation latency is the regulatory chain; the price the user gets is from t+ms.

Bottom line

With co-location and Anduin as a pure pass-through proxy, click-to-fill is two intra-datacenter hops — single-digit milliseconds, the same order of magnitude as the MM filling against its own book natively. The regulatory chain (DLT booking, confirmation back to the user) runs after the fill and never touches pricing: the user's price is locked at t+ms.
