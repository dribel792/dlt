Tokenised KO Certificates — MVP Blueprint

Flows · Architecture · Product tickets — the absolute minimum to get issuance off the ground · August 2026
The whole system in one sentence: one golden record per series drives document generation, token deployment and pricing; one daemon keeps strike/barrier current and fires the knock-out; everything the issuer publishes or acts on is written to an append-only archive.

1 · Flows

Four flows cover the entire product life. A is per-series, B is daily, C is continuous, D is terminal.

2 · Architecture

Four services, one contract, one database. Dashed boxes are external.

EXTERNAL

Market data feed

  • Reference price source named in Final Terms
  • One exchange feed is enough at MVP
BUILD

① Series registry + doc-gen

  • Golden JSON per series (CRUD + immutable after issue)
  • Final Terms renderer (template)
  • KID engine: SRI + performance scenarios (the only quant piece)
BUILD

② Pricing service

  • Spot feed in → bid/ask out per series
  • Public pricing API (REST + WS)
  • Writes every quote to archive
BUILD

③ Lifecycle daemon

  • Daily accrual: new strike/barrier per series
  • Barrier monitor on live ticks
  • KO executor: halt → residual → payout trigger
CHAIN

④ Token contract

  • Factory + per-series token (mint/burn/transfer)
  • Halt flag settable by keeper
  • The legal register of holders
SAVE

⑤ Archive (append-only)

  • Reference-price ticks
  • Published quotes
  • Strike/barrier history
  • KID versions + lifecycle events (mint, KO, payout + calc inputs)
EXTERNAL

Buyer / distributor

  • Bit2Me clients via DLT Finance
  • Consume pricing API + levels endpoint

Data direction: feed → ② and ③ · registry ① → ② ③ ④ (series params) · ② ③ → ⑤ (everything they publish or act on) · ③ → ④ (halt/KO) · buyer ↔ ② (quotes) and ↔ ④ (settlement). Postgres with insert-only tables covers ⑤ at MVP; the KID engine can start as a script run at issuance rather than a service.

3 · Product tickets

Five epics, ordered by dependency. Sizes: S ≈ days, M ≈ 1–2 wks, L ≈ 3+ wks. Critical path: E1 → E2 → E3/E4 in parallel → E5 hardening.

E1 · Series registry & document generation

foundation — everything depends on this
IDTicketSize
E1-1Define series schema (golden JSON): identifiers, underlying + reference source, strike, barrier, ratio, spread, dates, fees.AC: one schema validates all planned series types; record immutable after issuance except lifecycle fields.S
E1-2Registry service: create/read series, issuance state machine (draft → filed → live → knocked-out).AC: state transitions logged; no series can go live without Final Terms + KID attached.M
E1-3Final Terms generator — template rendered from registry record.AC: lawyer-approved template; output is byte-reproducible from the registry record.S
E1-4PRIIPs KID engine: SRI (Cat-3 VaR) + performance scenarios from ≥5y underlying history, cost tables; rendered in Spanish template.AC: results reproducible from stored inputs; every published KID versioned with validity window.L

E4 · Lifecycle daemon (accrual + KO keeper)

risk-critical — must run unattended
IDTicketSize
E4-1Daily accrual job: recompute strike/barrier per series at 00:00 UTC; write history; push to pricing.AC: idempotent (safe re-run); alert on missed run; levels never skip a day.S
E4-2Barrier monitor: evaluate every tick against current barrier per live series.AC: detection latency < 1s; survives feed reconnects; replays missed ticks after downtime.M
E4-3KO executor: store trigger evidence → halt on-chain → stop quoting → notify.AC: trigger tick + surrounding ticks archived before halt; whole sequence automatic.M
E4-4Residual value + payout: compute per Final Terms from hedge unwind, execute payout, burn tokens.AC: calc stored with all inputs; payout reconciles 1:1 with holder register; manual approval gate acceptable at MVP.M

E5 · Archive & operations

audit armor
IDTicketSize
E5-1Archive schema: insert-only Postgres tables for ticks, quotes, level history, KID versions, lifecycle events.AC: no UPDATE/DELETE grants; retention ≥ 7 years; nightly off-site backup.S
E5-2Chain indexer: mirror mint/burn/transfer events into archive (holder register copy).AC: archive register reconciles with on-chain state daily.S
E5-3Monitoring & alerting: feed health, accrual runs, keeper liveness, quote/halt status.AC: dead keeper or stale feed pages a human within 1 minute.S
Minimum viable launch = E1-1..3 + E2-1..3 + E3-1..3 + E4-1..3 + E5-1 — with E1-4 (KID engine), E2-4 (audit) and E4-4 (payout automation) allowed to finish during the prospectus approval window. The KO path (E4-2/3) and the tick archive (E3-1, E5-1) are the two things that must never be cut: issuance is a ceremony, but the knock-out is where the legal risk lives.
