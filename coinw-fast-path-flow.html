CoinW × Anduin — Integration Proposal

Fast-Path Execution: Latency-Optimized Flow for Securitized Perps on CoinW

November 2026 · Working draft v0.1 — direct issuer model: the client contracts directly with Anduin; CoinW provides the frontend and order transmission

This flow is built on the direct issuer model: CoinW provides the frontend (order capture & transmission, point-of-sale display), and the client's securities trade is contracted directly with Anduin — the issuer is the principal to every cert trade. There is no broker in between. Two tracks per order: (1) the quote stream goes MM → Anduin → CoinW directly, with Anduin as a thin validating proxy; (2) on order entry, CoinW fires a parallel hedge trigger straight to Anduin so the MM has already executed by the time the client order — transmitted by CoinW directly to Anduin — is matched and booked. The model is not RFQ — there is no per-order quote request and response. Anduin STPs / proxies everything straight into the MM; the MM's only job is to make sure the order executes.

1 · The principle — two tracks per order

TrackWhat runs on itLatency requirement
Fast path operational Quote streaming (MM → Anduin → CoinW) and the hedge trigger on order entry (CoinW → Anduin → MM). Carries no client order and no securities trade — it is the issuer's own hedging machinery, fed by an early signal from the distribution frontend. Milliseconds — co-located, WS/FIX, no intermediate consumer.
Order path contractual The client order and the securities trade: CoinW transmits the order directly to Anduin — the issuer is the counterparty of the cert trade, booked principal-to-client at Anduin, T+0. Not latency-critical — the price is already locked by the fast path when the order is matched; this track confirms and books.

Why the chain is this short

  • Client contract: the cert trade is a bilateral contract client ↔ Anduin (issuer as principal). No intermediary booking leg exists anywhere in the chain.
  • CoinW captures and transmits orders and renders the trading screen — it is never counterparty to the cert trade and never holds the instrument.
  • Assets: settlement runs client ↔ Anduin only; no party in the chain holds anything for anyone in the trade flow.

Why this kills the latency problem

In a multi-hop baseline, the MM quotes a price at T0 and fills the hedge at T0 + (multiple order hops) — the gap is MM risk, priced into the spread. In the fast path, the time between the user clicking and the MM filling is two co-located hops (CoinW → Anduin → MM, with Anduin proxying the MM's own execution API). The MM prices against a gap of milliseconds, not of a full multi-party round trip — so it can quote tighter spreads with less slippage reserve. And because the order path is CoinW → Anduin direct, even the booking confirmation is one hop.

2 · Quoting flow — straight MM → Anduin → CoinW

The MM streams the cert books (or perp books, per the integration flows doc) to Anduin, which proxies the stream directly to CoinW — rendered to the user as the reference price. Inline validation of the stream against Anduin's published levels is optional — Anduin is willing to skip it and run the checks asynchronously on the archived stream instead, keeping the proxy a pure pass-through; every tick lands in the insert-only quote archive either way.

3 · Execution flow — hedge trigger first, direct order transmission

On order entry CoinW does two things simultaneously: it fires the hedge trigger to Anduin (fast path) and transmits the client order to Anduin (order path — direct, since the client contracts with Anduin as principal). Both carry the same client_order_ref. There is no RFQ step — Anduin STPs / proxies the order straight into the MM, whose only job is to execute. Anduin matches the arriving client order to the locked MM fill by reference, fixes the cert execution price per the Final Terms formula, and books the trade principal-to-client T+0.

Timing summary

  1. t=0 — user clicks. CoinW stamps client_order_ref.
  2. t+ms — hedge trigger reaches the MM via Anduin's proxy; MM executes against the price it is itself streaming. Slippage window ≈ co-located round trip.
  3. t+ms — client order arrives at Anduin directly from CoinW (same co-located pair of hops); Anduin matches it to the locked fill and books principal-to-client T+0.
  4. t+ms+ε — execution details back to the user. The user's price and confirmation both come off the co-located path.

Bottom line

With co-location and Anduin as a pure pass-through proxy, click-to-fill is two intra-datacenter hops — single-digit milliseconds, the same order of magnitude as the MM filling against its own book natively. And because the order path is CoinW → Anduin direct, the confirmation is equally fast: there is no replay leg anywhere — nothing in the chain exists that could touch pricing or delay confirmation.
